# Delivery, Adoption, and Repository Consolidation Guide v0.2

**Status:** `proposed / no public execution authorized`

**Study:** `AILITW-IBERIA-2026`

## 1. Decision

Finish Hotel Shoreline before starting public-agent collection. Then create a
small field-research suite whose first purpose is to validate the instrument,
not rank companies. Promote only qualified field signatures into controlled
Hotel Shoreline analogues. Test a remedy on an external system only when its
operator authorizes access to an appropriate sandbox or deployment.

This sequence yields three products from one disciplined evidence pipeline:

1. a compelling Google Taskmaster submission;
2. reproducible native-adoption research; and
3. an ethical path from research to consulting, validation services, and
   eventually reusable software.

The defensible promise is:

> Observe native-adoption failure signatures responsibly, reproduce selected
> analogues against deterministic truth, measure targeted interventions, and
> help willing operators validate remedies in their own systems.

Do not promise a production fix, hidden-root-cause diagnosis, or universal
leaderboard from black-box observations.

## 2. Why this ordering wins the hackathon

The current [All Things Agentic rules](https://allthingsagentichackathon.devpost.com/rules)
require Gemini 3.5 or newer, a listed Google agent framework, and a Google Cloud
service. The Taskmaster criterion emphasizes completing a multi-step workflow,
and the submission requires reproducible setup, architecture, and a demo of the
Google Cloud backend. Re-verify the
[official FAQ](https://allthingsagentichackathon.devpost.com/details/faqs) and
rules immediately before submission.

Hotel Shoreline should therefore lead with what judges can see in four minutes:

- a multilingual, compound operational request;
- a Gemini/Genkit candidate task graph;
- validation, decomposition, constraints, tool calls, and lifecycle evidence;
- verified actions rather than a text-only completion claim;
- a matched baseline/intervention comparison;
- durable run history and an inspectable export; and
- Cloud Run execution plus accurate disclosures.

The Iberia protocol can appear as the credible follow-up and community-impact
roadmap. Public collection must not delay or overcomplicate the submission.

## 3. Evidence and intervention ladder

| Level | Environment | Activity | Permitted conclusion |
| ---: | --- | --- | --- |
| E0 | Hotel Shoreline deterministic | Verify schemas, measures, lifecycle, and tools | The method behaves as specified. |
| E1 | Hotel Shoreline + Gemini baseline | Run frozen matched cases | Baseline behavior under declared controlled conditions. |
| E2 | Hotel Shoreline + intervention | Run preregistered treatment and holdouts | Controlled causal effect for the tested analogue and configuration. |
| E3 | Public production surface | Low-volume black-box observation | Externally observable behavior under the recorded access conditions. |
| E4 | Cross-system field study | Reviewed, repeated, matched observations | Scoped patterns in the eligible sample; no hidden-root-cause claim. |
| E5 | Operator-authorized environment | Matched baseline/remedy validation | Effect in the operator's tested system and authorized conditions. |

Evidence may flow upward only after the preceding quality gate. E2 and E4 are
complementary and neither substitutes for E5.

## 4. Program delivery sequence

### Phase A — Hotel Shoreline release

**Issues:** `HSD-007 -> HSD-006 -> HSD-008`

**Exit:** a deployed, reproducible Taskmaster demo with a frozen comparison,
append-only evidence, sanitized export, architecture diagram, four-minute
narrative, and honest release claims.

**Non-goals:** public-agent benchmark, company ranking, operator outreach, and
production-fix claims.

### Phase B — Minimum viable field suite

Build only the research primitives the pilot needs:

```text
target manifest + access audit
  -> versioned semantic cases and language variants
  -> manual observation importer
  -> immutable evidence and artifact references
  -> pure versioned evaluators
  -> review/adjudication records
  -> aggregate analysis and sanitized export
```

This is initially a file/CLI/library workflow, not a crawler or dashboard.
Automation is earned only after repeated manual work has a stable target,
permission basis, schema, and failure boundary.

### Phase C — 27-cell feasibility pilot

Select three currently accessible systems only after the access audit. For each,
test three mission families across `en`, `es-ES`, and `pt-PT`:

1. constraint-rich discovery or decision;
2. conditional/negative capability boundary; and
3. corrective multi-turn recovery or escalation boundary.

That produces 27 attempted cells. Repeat only material failures, disputed
scores, false-resolution candidates, and a stratified success control, up to
three attempts per promoted condition.

The pilot may report instrument feasibility, eligible denominators, reviewer
agreement, and candidate failure signatures. It may not report a leaderboard,
agent-level parity rate, or Reliable Autonomy Ceiling unless the protocol's
sampling gates are independently satisfied.

### Phase D — Focused field study

Proceed only if the pilot proves stable access, meaningful observability,
adequate language review, reproducible adjudication, and a valid publication
boundary. Expand selectively from the 70-seed library. Freeze the cohort,
reference condition, exclusions, repetitions, and analysis plan before
production collection.

### Phase E — Controlled analogue and treatment study

For each promoted field signature:

1. remove company-specific and personal information;
2. preserve the mission, critical state, failure opportunity, and consequence;
3. create deterministic fictional truth in Hotel Shoreline;
4. freeze the Gemini/Genkit baseline before inspecting treatment results;
5. test one interpretable intervention at a time;
6. retain invalid, failed, timed-out, and unavailable attempts;
7. evaluate unseen holdouts and cross-language regressions; and
8. label the result a controlled analogue, never a production reproduction.

### Phase F — Publication and cooperative engagement

Publish aggregate findings, methods, analysis code, limitations, amendments,
and sanitized evidence sufficient for reproduction. Before system-specific
publication, apply the approved naming, notification, evidence-retention,
factual-correction, and responsible-disclosure policy.

An operator brief should separate:

- observable facts and evidence;
- researcher interpretation and uncertainty;
- the controlled Shoreline analogue;
- the tested intervention and its limits;
- proposed operator-side validation; and
- factual corrections or operator response.

### Phase G — Operator-authorized validation

If an operator engages, create a new scoped protocol and agreement. Test only
in an authorized sandbox or approved deployment boundary, establish its own
baseline, success criteria, privacy/security controls, and rollback plan, then
run a matched remedy evaluation. This is the first stage that can support a
causal statement about an external agent.

## 5. Product and commercialization ladder

Commercialization follows evidence maturity rather than preceding it:

| Offer | Evidence required | Deliverable |
| --- | --- | --- |
| Public research | E0–E4 with publication gates | Reproducible report, methods, taxonomy, and aggregate findings. |
| Native Adoption Snapshot | Valid public or customer-provided evidence | Fixed-scope journey/locale risk map and prioritized hypotheses. |
| Native Adoption Analysis | Operator participation | Reviewed evaluation, failure signatures, and remediation plan. |
| Intervention Validation | Authorized test environment | Matched baseline/treatment evidence, regressions, and decision memo. |
| Readiness & Regression Program | Repeated operator need | Versioned corpus, CI/eval gates, monitoring, and periodic reviews. |
| Native Agent product | Repeated cross-customer primitive | SDK/CLI/hosted capability with a stable owner and maintenance case. |

Paid work does not buy favorable findings. Public research, private customer
evidence, and product telemetry remain distinct data and governance domains.

## 6. Repository ownership and boundaries

| Concern | Owner | Rule |
| --- | --- | --- |
| Domain-neutral contracts, graph validation, execution evidence | `native_agent_sdk` | No company, locale, provider, or study concepts. |
| Fictional hotel world, Gemini/Genkit adapter, demo UI | `hotel_shoreline` | No public crawler or third-party evidence warehouse. |
| Study protocols, targets, cases, observations, evaluations, reports | `research/ailitw` | No runtime dependency from product packages. |
| Company/product positioning and service definitions | `research/canon/` and `docs/product/` | Claims link to versioned evidence; no demo-specific implementation. |
| Historical source material | Git history | Not an active authority. |

Evaluation remains separate from intervention. Evaluators consume immutable
evidence and emit versioned derived records. Intervention specifications state
a hypothesis and treatment but cannot rewrite evidence or activate themselves.

Consolidation decisions:

- D003 records the former-tree migration and Git recovery boundary;
- exact duplicates, generated artifacts, superseded planning snapshots, and
  stale instructions were removed by REP-001;
- make each fact authoritative in one document and link to it elsewhere;
- keep roadmaps outcome-oriented and issues implementation-ready;
- keep raw/private research artifacts ignored or access-controlled; and
- cleanup remained separate from the delivered HSD-005 feature branch.

## 9. First implementation decision after HSD-008

Start `AILITW-001`, not the field-suite code. Its output is a signed-off target
and access manifest, an ethics/publication decision record, reviewer plan, and a
frozen 27-cell pilot. If fewer than three systems support fair, permitted,
observable multilingual testing, narrow the study or replace targets; do not
manufacture comparability.

Until those gates pass, this guide is an adoption and consolidation target—not
authorization to test public systems, contact operators, publish company-level
claims, or build a crawler.
