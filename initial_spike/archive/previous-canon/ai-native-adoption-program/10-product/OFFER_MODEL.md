# Offer Model

ID: `DOC-PROD-0003`
Version: v0.2
Status: proposed

## Purpose

This document defines the initial offer model for packaging AI Native Adoption Program capabilities.

## Offer Principle

An offer is a repeatable package of capability, evidence, delivery process, and claim boundaries.

## Offer Types

### Assessment Offer

Purpose: identify native adoption failures in a product, agent, or workflow.

Possible deliverables:

- journey review
- failure map
- adoption scorecard
- evidence inventory
- risk and trust notes
- prioritized treatment candidates

### Benchmark Offer

Purpose: produce repeatable journey-based tests across languages, locales, systems, or treatments.

Possible deliverables:

- benchmark journey set
- baseline report
- human evaluation packet
- metric table
- failure taxonomy mapping
- limitations statement

### Treatment Offer

Purpose: implement and test a black-box adaptation layer.

Possible deliverables:

- treatment protocol
- prompt, router, repair, or tool-mediation package
- baseline versus treatment comparison
- rollback criteria
- implementation notes

### Trust Review Offer

Purpose: evaluate whether evidence and claims are reliable enough for internal or customer-facing use.

Possible deliverables:

- evidence integrity review
- evaluator reliability review
- claim readiness assessment
- unsupported-claims list
- audit trail packet

### Platform Starter Offer

Purpose: help a team set up the local-first operating system.

Possible deliverables:

- registry templates
- runner skeleton
- evidence storage convention
- dashboard or review workflow
- initial closed-loop setup

## Offer Record

Each offer should include:

- `offer_id`
- title
- offer type
- target customer or user
- problem statement
- included capabilities
- required inputs
- deliverables
- evidence level
- trust requirements
- supported claims
- unsupported claims
- delivery steps
- readiness state
- owner

## Delivery Pattern

1. Intake: define product, language contexts, target journeys, and risks.
2. Scope: select the smallest useful loop.
3. Baseline: observe or benchmark current behavior.
4. Diagnose: classify failures and identify likely mechanisms.
5. Treat: choose or build the smallest external intervention.
6. Retest: compare baseline and treatment.
7. Review: apply evidence and evaluator reliability checks.
8. Package: deliver findings, artifacts, and claim boundaries.

## Claim Boundaries

Every offer must separate:

- what the evidence supports
- what appears promising but unvalidated
- what was not tested
- what failed or regressed
- what should not be claimed externally

## First Offer Candidate

Start with an internal pilot offer:

`Native Adoption Closed-Loop Assessment`

Narrow scope:

- one journey
- three to five languages
- two agent systems
- one baseline run set
- one Sandbox treatment
- one Wild-style retest

Success is proving the delivery loop, not maximizing coverage.
